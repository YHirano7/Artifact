L3 ローカルLLMでハーネスを自作する

ハーネス自作は「どの層で何を縛るか」の設計 ― 形式はデコードで、行動はループで、正しさは外側の検査で縛る

ローカルLLMでは、クラウドのツールが隠していた層（推論サーバ・テンプレート・デコード・ループ）を自分で組む。そのぶんL1の⑤（デコード）にまで決定論の制約を差し込める。引き算モデルの各層が、コードのどこに対応するかを示す。

土台（性能・容量を決める層） 決定論で縛れる層 確率が残る部分 落とし穴 L0（引き算モデル）への接続

自分で実装・設定するもの
L0での位置
F. 外側の検査と評価
結果が正しいかを判定する
  • 型・Lint・テストを自動で回し、失敗をループに差し戻す
  • 決まったタスク集で回帰評価する。temperature 0でも出力は揺れうるので1回の成功で判断しない。計算の並べ方を揃える工夫で1,000回すべて同一出力にできた例もある [10]
  • 同じ失敗が出たら、指示（ガイド）・検査（センサー）のどちらを足すかを決めて更新する [11]
② センサー③ 人
E. コンテキスト管理
何を載せるかを規則で決める
  • 指示ファイルの読み込み規則（applyTo 相当のglob照合）を自分で書く
  • 履歴の要約・切り詰め、ツール結果の長さ上限、重要な決定のファイルへの書き出し
  • 外部ツールはMCPで接続できる。サーバには会話全体を渡さず、境界はホスト（自分のハーネス）が管理する [9]
① ガイド
D. エージェントループ
生成→解析→関所→実行→追記
  • まず「決まった手順で呼ぶワークフロー」で足りないかを検討し、足りないときだけモデルに手順を任せる [7]
  • ツールは説明を読めば使い方が分かり、誤用しにくい形にする（例：相対パスを受け付けず絶対パスを必須にする）[7]。エージェント向けにインターフェースを設計し直すだけで成績が上がった例 [8]
  • 実行前に許可リストで判定し、実行はサンドボックス内で。回数上限と終了条件を必ず持つ [12]
② 関所
C. デコード制約
選べるトークンを文法で絞る
JSON Schemaや文法（GBNF）を渡すと、毎ステップ、文法に違反するトークンの確率を0にしてから選ぶ [5][6]。ツール呼び出しのJSONが壊れない、ツール名が定義済みのどれかになる、といった形式を保証できる。
通常（{"tool": " の次）

保証されるのは形式だけで、中身の正しさ（どのツールを選ぶのが妥当か）は確率のまま。スキーマはモデルには見えないので、プロンプトでも構造を説明する [5]
最も内側の決定論
B. プロンプト整形
会話を1本のトークン列にする
  • 役割付きのメッセージとツール定義を、モデル固有のチャットテンプレート（特殊トークン入りの形式）で1本の列に変換する [4]
  • 学習時と違う制御トークンを使うと性能が大きく落ちる。応答開始の印（add_generation_prompt）を付け忘れると、モデルが依頼文の続きを書き始める [4]
前提条件
A. 推論サーバ
モデルを読み込み、計算する
  • llama-server（llama.cpp）・Ollama・vLLMなど。多くはOpenAI互換APIを持つので、ハーネス側は共通の形で呼べる
  • 文脈長を決める。Ollamaの既定はVRAM 24GiB未満で4kトークンで、エージェント用途には64k以上が推奨されている [3]
  • KVキャッシュ（文脈の計算結果の保持領域）の管理が性能を左右する。従来実装では確保したKV領域の約2〜4割しか実際に使われておらず、ページ管理で無駄を減らすとスループットが2〜4倍になった [1]
容量・速度
最小の始め方：A（推論サーバ）とB（テンプレート）は既存のサーバに任せ、OpenAI互換APIの上でC〜Fを書く。llama-server は /chat/completions の response_format にJSON Schemaを渡せるので、Cもまずはこれで足りる [5]。自前で持つべきなのは、E（何を載せるか）・D（何を許すか）・F（何で判定するか）という、リポジトリ固有の判断が入る層

メモリ予算：文脈の長さはVRAMで決まる

項目見積もり式計算例
重みパラメータ数 × ビット/重み ÷ 88Bモデル・4.5ビット（Q4_K）→ 約4.5GB。16ビットなら約16GB [2]
KVキャッシュ2 × 層数 × KV次元 × バイト数 × トークン数 [1]層32・KV次元1024・16ビット → 1トークン128KiB → 32kトークンで約4GiB
論文の例：13Bモデル（16ビット）で1トークン約800KB、2,048トークンで約1.6GB [1]
量子化形式F16Q6_KQ5_KQ4_KQ3_KQ2_K
ビット/重み [2]166.565.54.53.442.63
判断軸：ビットを下げるほど重みは小さく速くなるが、品質は下がる。浮いたVRAMを文脈長に回すかどうかは評価（F層）で決める

最小ハーネスの骨格（擬似コード）

msgs = [SYSTEM, *load_instructions(target_files)]  # E: 規則で選ぶ
for step in range(MAX_STEPS):                      # D: 回数上限
    prompt = chat_template(msgs, TOOLS)            # B: 整形
    out = llm(prompt, json_schema=TOOL_CALL)       # C: 形式を保証
    call = parse(out)
    if call.is_final: break
    if not policy.allows(call):                    # D: 関所
        msgs.append(denied(call)); continue
    result = sandbox.run(call)                     # D: 隔離して実行
    msgs += [call, truncate(result)]               # E: 追記・切り詰め
report = run_lint_and_tests()                      # F: 外側の検査
確率が入るのは llm(...) の1行だけ。残りはすべて普通のプログラムで、テストできる

自作でつまずきやすい点

文脈長が既定のまま指示やファイルが収まらない。ollama ps で割り当て量を確認 [3]
テンプレートの不一致エラーは出ないのに品質だけ落ちる [4]
スキーマの説明漏れ形式は通るが中身が的外れになる [5]
ツールの入れすぎツール定義だけで文脈を圧迫する [7][9]
1回で評価揺らぎを見落とす。複数回で分布を見る [10]

引き算モデル（L0）を自作ハーネスに実装すると ― 内側から外側へ

C. デコード制約
文法外のトークンを選べなくする形式：確実／内容：保証なし
→
E. 文脈の組み立て
指示・用語集・ADRを規則で載せる（①）載るのは確実／効くのは確率
→
D. ループの関所
許可リスト・サンドボックス（②）行動：確実に止まる
→
F. 外側の検査
型・Lint・テスト・評価（②）結果：検査した範囲は確実
→
人のレビュー
意図・テストの妥当性（③）機械で判定できない残り
L0への接続：クラウドのツールではCとDの一部が提供側に隠れているため、利用者は①（E）と②（D・F）を中心に設計する。ローカルではCまで手が届くので、引き算の層が1つ増える

L1〜L3を通した結論：引き算モデルが妥当と言える理由

L1モデルは文脈を条件に確率的に続きを書くだけ。固有の知識は文脈でしか届かず、届けても保証はない → ①は「寄せる」しかできない
L2何を載せるか・何を実行するかはハーネスが規則で決める → ②はモデルの外に置けば確実に効く
L3確率が入るのは生成の1行だけで、残りは普通のプログラム → 制約は層ごとに設計・テストできる
