① 計算リソース＆潜在変数 なぜ <think> トークンを出すと賢くなるのか System 1 → System 2 [Weng 2025]
・計算深さの動的拡張：Transformerが1トークン出すFLOPsは問題難易度によらず一定（約 2N）。回答前に思考トークン列 z = (z_1, ..., z_m) をDecode生成させると、各思考トークンのK/VテンソルがKVキャッシュ（作業記憶）に蓄積され、後続トークンがそれにAttendすることで実質的な直列計算回路の深さが m ステップ拡張される。
・潜在変数周辺化：回答確率 P(y|x) = ∑_z P(y|x, z) P(z|x) において多様な思考経路 z をサンプリング・検証・修正する問題として統一される［Lilian Weng 2025］。
② Compute-Optimal Scaling Sequential（直列修正）vs Parallel（PRM並列探索） 効率 4× 改善・14× 大モデル凌駕 [Snell+ 2025]
・Process Supervision (PRM)［Lightman+ ICLR 2024］：最終答のみを監督するOutcome Supervisionより、各推論ステップを採点するPRMがMATHで 78.2% vs 72.4% と圧倒。
・難易度適応配分［Snell+ ICLR 2025］：簡単な問題は純粋な直列修正（Sequential Revision）が最良だが、難問は多様性確保のため並列サンプリング（PRM探索）と直列修正の最適比率が存在する。難易度に応じた適応配分でBest-of-N比 4×以上効率化し、FLOPs一致条件で 14倍大きいモデルを上回る（ただし未学習モデルの素の自己修正は逆に劣化する［Huang+ ICLR 2024］）。
③ Budget Forcing (s1) 終了デリミタ抑止と "Wait" 注入によるデコーダ直接制御 1,000問SFTでo1-preview超え [Muennighoff+ 2025]
厳選1,000問（s1K）でSFTした s1-32B に対し、推論デコーダ側でテスト時計算量を強制制御する：
・Scaling Down（早期打切）：思考トークン上限に達したら終了タグ </think>（または終了デリミタ）を強制Prefill追記して即座に最終回答へ移行させる。
・Scaling Up（思考延長）：モデルが </think> を出そうとした瞬間にそのLogitをマスク（抑止）し、代わりに文字列 "Wait" を現在の推論トレース末尾へ追記して再点検を促す（2x/4x/6x延長でAIME24が 50.0% → 56.7% へ伸長し自己修正が発動）。

層B：Reasoning強化学習（GRPO・DeepSeek-R1・Dr. GRPO） なぜPPOではなくGRPOで長い思考が創発したのか
GRPO（Group Relative Policy Optimization）［Shao+ 2024 / DeepSeek-R1 2025 A.3］ Value (Critic) モデル完全撤廃
【GRPOのグループ相対Advantage】 質問 q ごとに旧方策から G 個の出力 {o_1..o_G} をサンプルし、A_i = (r_i - mean(r)) / std(r) でAdvantageを算出。Policyと同サイズのValueモデルが不要になりメモリ・計算量を大幅削減。 省メモリ・高スケーラビリティ
【なぜPPOは長CoTに不向きか①：Value予測の破綻［DeepSeek-R1 L831-835］】 長いCoTでは途中で内省・方針転換（revision）が起き初期の推論が後から覆されるため、部分トークン列から最終報酬を当てるValueモデルの学習自体が困難を極める。 内省・覆しとの相性
【なぜPPOは長CoTに不向きか②：累積KLによる長さ罰則［DeepSeek-R1 L837-848］】 PPOは各トークン報酬にKLペナルティを加えるため、累積KL罰則が暗黙に「応答長そのものへのペナルティ」となり思考トークンが伸びない。GRPOはSchulman不偏推定器 D_KL をLossに直接加算するため長さを不当に抑圧しない。 思考トークン伸長の鍵 ★
【DeepSeek-R1-Zero の Aha Moment と R1 の4段階進化［DeepSeek-AI 2025］】 SFTなしの純粋RL（Accuracy＋Format報酬のみ）で思考長が自律伸長し、内省で "wait" が急増する Aha Moment が創発（AIME24: 15.6%→71.0%）。R1は①Cold-Start SFT → ②Reasoning RL → ③Rejection Sampling SFT → ④全領域RLで言語混在を解消。 教師なし自己検証創発
⚡ Dr. GRPO が暴いた「GRPOの長さバイアス」［Liu+ COLM 2025 arXiv:2503.20783］：
標準GRPOの目的関数にある 応答長 1/|o_i| での除算 は、正答（A_i > 0）では短い応答に大きな勾配を与え、誤答（A_i < 0）ではペナルティを薄めるために無意味に長い応答を選好させる最適化バイアスを生む。Dr. GRPOは |o_i| と std(R) の正規化項を除去し、誤答の冗長化を止めてトークン効率を劇的に改善した。

層C：ハーネス統合（Extended / Interleaved / Preserved Thinking） 思考ブロック・KVキャッシュ・ツール選択の厳密規約
④ Interleaved Thinking ツール呼び出し間の思考と単一アシスタントターン構造 Adaptiveで自動有効 [Anthropic Docs]
ツール使用ループ全体が1つのアシスタントターンを構成する。Interleaved Thinking により、[thinking_1] + [tool_use_1] → (tool_result_1) → [thinking_2] + [tool_use_2] → [text] のように各ツール結果を受け取るたびに思考ブロックを挟み、観察結果の分析と次手決定を行える（Manualモードでは interleaved-thinking ヘッダで budget_tokens > max_tokens も許容）。
⑤ Preserved Thinking & KV Cache 暗号化 signature の前方プレフィックス検査 改変で400エラー＆キャッシュ破棄
・Signatureと無改変返送：各 thinking ブロックには完全な推論過程を暗号化した signature フィールドが付く。ツール結果を返す際は前回の thinking（および redacted_thinking）を1文字も変えず返送しなければならない。
・Prefix Check とキャッシュ連動［Anthropic Docs L582-608］：APIは①生成モデル互換性と②それより前の全プレフィックス（System・Tools・過去Messages）が不変かを検証する。前方プレフィックスを編集すると思考ブロックが無効化されると同時にKVキャッシュも壊れる。また thinking 設定や effort 変更もプロンプト先頭に描画されるためキャッシュが全滅する。
⑥ Response Prefill / 強制ツールとの衝突 なぜ Thinking 時代に Prefill が使えないのか Claude 4.6+ は Prefill 400 エラー
Thinking有効時は応答の先頭が [thinking] ブロックで始まる必要があるため、アシスタント応答の Response Prefill や Manual Thinking での強制ツール選択（tool_choice: any / tool）はエラーで拒否される。Adaptive Thinking等で強制ツール選択が通る場合も思考ブロックがスキップされ直接ツール呼出から始まる。思考させつつ確実にツールを呼ばせるには tool_choice: auto ＋ Strict Tool Use（CFG Logitマスク） を使う［Anthropic Docs L707］。

（並列サンプリング）		 Best-of-N / Self-Consistency /

1. ツール定義の動的追加・削除・順序変更 × 全滅：先頭ブロックのハッシュが変わり以降の全履歴キャッシュが失効 スキーマ再コンパイル（FSM/PDA再構築）のTTFTオーバーヘッド発生 NG 前方プレフィックス変更により過去ターンのPreserved Thinking署名も無効化。ツール定義は固定せよ［Manus / Anthropic］
2. Response Prefill によるツール強制
（<tool_call>{"name":..）		 ◎ 温存：ツール定義を変えないため先頭KVキャッシュは100%ヒット アシスタント応答先頭を固定し後続トークンの探索空間を制限（要Token Healing） 衝突 Thinking有効時およびClaude 4.6以降では400エラーで拒否。非ThinkingのローカルLLM（Hermes/vLLM等）専用の技法
3. API tool_choice 強制
（any / tool 指定）		 ◎ 温存：ツール定義自体は不変 デコーダ側でツール呼出開始トークン以外のLogitをマスク 注意 Manual Thinkingではエラー。Adaptive Thinking等で通る場合も[thinking] がスキップされ無思考でツールを呼ぶ［Anthropic Docs L399, L707］
4. tool_choice: auto ＋ Strict Structured Outputs ◎ 温存：プレフィックス不変（文法キャッシュも再利用） ◎ 最適：[thinking] 終了後の tool_use JSON引数部分にのみCFGマスク適用 推奨 ★ Interleaved Thinkingで十分思考させた後、100%スキーマ準拠のツール呼出を出させる現代の標準パターン［Anthropic Docs L707］
5. ターン途中での thinking / effort 設定変更 × 全滅：設定値がシステムプロンプト先頭に描画されるためキャッシュ破棄 temperature / top_k 等の非互換パラメータ指定は400エラー NG 1つのツールループ（アシスタントターン）内でThinking設定を切り替えてはならない（変更はメッセージ内システム指示で行う）
6. 過去メッセージの要約・削除（Compaction） △ 再構築：編集位置以降のKVキャッシュが破棄され新規プレフィックス開始 影響なし 注意 編集位置より後ろの thinking ブロックはPrefix Check違反で無効化。Keep-allモデルでは無改変追記を維持し閾値到達時のみ一括Compactする

② s1K データ選別の3原則 59K → 1,000問

⑤ CoTへの直接最適化の罠 Faithfulness
思考過程（CoT）自体に強い検閲や報酬モデル（PRM）をかけすぎると、モデルは「監視者を騙す綺麗だが不誠実な思考（Unfaithful CoT / Reward Hacking）」を学習してしまう。DeepSeek-R1が結果報酬（Accuracy＋Format）のみに絞った理由もここにある。
出典: Lilian Weng "Why We Think" (2025) / DeepSeek-R1
⑥ Thinkingとサンプリング制約 API 400 エラー防止
Reasoningモデルでは確率分布の勝手な変形が思考連鎖を壊すため、Thinking有効時（およびClaude最新世代）は temperature や top_k の変更が禁止（400エラー）されている。出力の制御はサンプリング温度ではなく effort とプロンプトで行う。
出典: Anthropic Docs "Thinking" L701-704
概念比較①：Outcome Supervision (ORM) vs Process Supervision (PRM) vs Verifiable Rewards (RLVR) Lightman+ (2024) / DeepSeek-R1 (2025)
ORM：最終解答の正誤だけを学習した報酬モデル（途中の誤推論を見逃しやすい）。PRM：人間のステップ単位ラベル（PRM800K等）で各行の正誤を採点する報酬モデル（探索に強いがラベリング高コスト・Reward Hackingリスク）。
RLVR（DeepSeek-R1）：ニューラル報酬モデルを使わず、数学の厳密一致やコンパイラ/単体テスト通過などの決定論的ルール報酬だけでGRPOを回し自己検証を創発させる。
概念比較②：Extended Thinking（手動予算）vs Adaptive Thinking（自律判断）vs Interleaved Thinking（ツール間） Anthropic Claude Docs
Extended Thinking（Legacy）：開発者が budget_tokens を固定指定し必ず先頭で思考させる方式。
Adaptive Thinking：モデル自身がプロンプト難易度に応じて思考の有無と長さを自律決定する方式。Interleaved Thinking：単一ターン内の複数回ツール呼出の合間（tool_result 受領直後）にも思考ブロックを挟む方式（Adaptiveでは自動内包）。
概念比較③：ハーネス設計の世代交代 — Response Prefill 時代 vs Reasoning + Strict CFG 時代 Manus (2025) → Anthropic (2026)
第1世代（非Thinking）：アシスタント応答先頭に <tool_call>{"name": "browser_ をResponse PrefillしてLogit空間を直接縛る［Manus 2025］。
第2世代（Reasoning / Interleaved Thinking）：先頭に [thinking] が入るためPrefillは不可。tool_choice: auto で思考ブロックを自由に生成させ、続く tool_use ブロックの引数生成時にXGrammar等のCFG Logitマスクを適用する。
