推論＆出力制御・初級 / Rank 0

LLMの応答は「まとめ読み（Prefill）→ 1語ずつの確率くじ引き（Decode）」の反復であり、計算メモ・違反くじ除外・下書きの3つで制御する

対象：数式なしで掴む「①KVキャッシュ → ②Logitマスク → ③思考トークン」の基礎地図
初級の核心結論：LLMは一度に全文を作っているのではなく、「ここまでの文脈を読んで、次に来る1トークン（約3〜4文字）をくじ引きで選び、末尾に足してまた最初から読む」というループを何百回も回している。この仕組みを知ると、なぜキャッシュで10倍安くなり、なぜJSONが壊れ、なぜ <think> で賢くなるのかが一本の線で繋がる。
① Prefill（まとめ読み）とKVキャッシュ Decode（1語ずつ出力）とメモリ運搬 ② Logits（点数）と確率くじ引き Logitマスク（違反くじを0%に除外） ③ 思考トークン（下書き）と強化学習 初学者がハマる3大トラブル
Step-by-Step Guide to LLM Inference（プロンプトが入ってから1語ずつ返事が出てくるまでの9ステップ全体地図） この1枚（Rank 0）で全体像を掴んでから、中級（Rank I）→ 上級（Rank II）→ 特級（Rank III）へ進むと数式・論文がすんなり読める
ステージ①：読む工程（Prefill）と書く工程（Decode）と「計算メモ（KVキャッシュ）」 なぜ2語目以降は「計算」より「運搬」が大変なのか
Step 1 トークン化（Tokenization）：文章を「番号つきの言葉の破片」に割る 語彙数 約5万〜13万個
LLMは文字をそのまま読めず、トークナイザ（BPE等）で数文字ずつの破片（トークン）に分割しID番号に変換する。例えば "This is a fine day." は [1212, 318, 257, 3734, 1110, 13] の6個の番号になる［Guidance Docs］。英語では空白を含めた " fine" で1トークンになることが多い。
Step 2 Prefill（最初のまとめ読み）vs Decode（1語ずつの書き出し） TTFT と TPOT
・Prefill（1語目が出るまで＝TTFT）：入力プロンプト（例：1,000語）は最初から全部わかっているので、GPUの電卓をフル動員して1回で一気に並列計算できる（計算勝負＝Compute-bound）［NVIDIA Blog / Databricks］。
・Decode（2語目以降＝TPOT）：前の1語が出ないと次の1語が計算できないため、1語ずつ順番に出す。1語出すたびに巨大なモデル重み（数十GBの辞書）を倉庫（HBMメモリ）から毎回運び直すため、電卓が暇になりデータ運搬待ち（Memory-bound）になる。
Step 3 KVキャッシュ（計算メモの使い回し）と「料金10倍差」のカラクリ $3.00 → $0.30/MTok
1語追加するたびに過去の文章をゼロから計算し直すと、100語出すのに5,050回分のムダ計算が発生する［Cobanov］。そこで一度読んだ各トークンの「検索ラベル（Key）」と「意味の中身（Value）」をGPUメモリにメモして使い回すのが KVキャッシュ。さらにAPI（Claude等）でも前回のリクエストと先頭が一字一句同じならこのメモを再利用できるため、入力トークン料金が1/10（10倍差）になり応答開始（TTFT）も最大85%速くなる［Manus 2025 / Anthropic Docs］。
⚡ 初級の鉄則①：KVキャッシュは「先頭からの順番」に依存する。システムプロンプトの先頭に「現在時刻（秒）」を入れたり、途中でツール定義を消したりすると、その場所から後ろの計算メモがすべて無効（再計算＝10倍コスト）になる［Manus 2025］。

ステージ②：次の1語を選ぶ「確率くじ引き」と「違反くじの物理除外（Logitマスク）」 どうやってJSONや関数呼び出しを100%守らせるのか
1トークンが決まる4段階：Logits（生の点数）→ Mask（違反除外）→ Softmax（確率％）→ Sample（くじ引き） 毎ステップ1語ずつ実行
【Step 4：Logits（ロジット）と Temperature（温度）】 LLMは辞書にある全トークン（約10万語）に「次に来そうか」の生の点数（Logits）をつける。温度（Temperature）を低くすると1位の独走になり、高くすると2位以下にもチャンスが回る。 Softmaxで合計100%に変換
【Step 5：サンプリング（Top-k / Top-p / Min-p）】 確率0.001%の「変な単語（ハズレくじ）」が箱に残っていると、長文の途中で急に意味不明な語を引いてしまう［Holtzman+ 2020］。そこで上から確率合計90%まで（Top-p）や、1位の確率の1割以上（Min-p）だけを残して他を捨てる。 ハズレくじの事前カット
【Step 6：Constrained Decoding（制約付きデコード / Logitマスク）】 プロンプトで「JSONだけ出して」と頼んでも、"Sure!" の確率は0%にならない。Outlines や XGrammar は、文法ルール（オートマトン）を使って「今この位置でJSON違反になる全トークン」の点数を -∞（確率 0%）に書き換える［XGrammar Docs / Qiita］。 100% 構文エラーゼロ ★
【具体例：数字しか許されない位置でのLogitマスク】 スキーマが "age": の直後なら、"25" や "3" 以外の全トークン（"twenty" や "abc"）の確率を0%にマスクしてからくじを引くため、絶対に型違反が起きない［LMSYS 2024］。 物理的に違反語を選べない
⚡ 初級の鉄則②（Response Prefill と境界の罠）：
LLMの返事の1語目に <tool_call>{"name": "browser_ までを人間側であらかじめ書き込んでおく（Response Prefill）と、続きから生成が始まるため特定のツール群だけを強制できる［Manus 2025］。ただし単語の途中で不自然に切るとトークン分割が狂うため、1語巻き戻して繋ぎ直す Token Healing が使われる［Guidance Docs］。

ステージ③：考えてから答える「思考トークン」と強化学習（Test-Time Compute） なぜ「下書き」を書かせると14倍大きいモデルに勝てるのか
Step 7 なぜ「即答」だと間違うのか：1トークンあたりの計算量は常に一定 暗算で即答するのと同じ
人間が "12345 × 56789 は？" を1秒で即答できないのと同じで、Transformerが1トークンを出すときに使える計算量（掛け算の回数）は、簡単な挨拶でも数学オリンピックの難問でも常に同じに固定されている［Lilian Weng 2025］。だから、いきなり最初の1語目で最終解答を出させようとすると計算が足りずに間違える。
Step 8 思考トークン <think>：KVキャッシュを「計算用紙（下書き）」にする Test-Time Compute スケーリング
最終回答を出す前に、<think> まず条件を整理すると… いや待てよ(Wait)、計算し直そう… </think> と何百〜何千トークンもの「考える過程」を1語ずつDecode生成させる。書き出した思考トークンはすべてKVキャッシュ（作業記憶）に蓄えられ、自分の下書きを読み返しながら次の推論を進められる。こうして「推論時の計算量（Test-Time Compute）」を増やすと、小さなモデルでも14倍巨大なモデルを上回る精度が出せる［Snell+ ICLR 2025］。
Step 9 DeepSeek-R1 と GRPO：どうやって「見直す力」が自然に生まれたのか Aha Moment（ひらめき）の創発
人間が思考のお手本を書かなくても、1つの問題に対してモデルに複数個（グループ G 個）の解答を出させ、「最終の答えが合っていた解答」をグループ平均と比べて褒める強化学習（GRPO）を繰り返すだけで、モデルは「長く考えて途中で "Wait" と検算した方が正解率が上がる！」と自ら気づき、自己検証する能力を獲得した［DeepSeek-R1 2025］。

ハーネス実務でよく聞くルール 推論エンジンの裏側で何が起きているか（原因） やらないとどうなるか ／ 正しいやり方
疑問①：なぜ「プロンプトは追記のみ（Append-only）」にして先頭を固定するのか？ 推論エンジン（vLLMやSGLang）は、プロンプトを先頭から16語ずつのブロックに分け、「前のブロックのハッシュ＋今のブロックの語」を鎖のように繋いでKVキャッシュを検索しているため［vLLM Docs］。 ・NG：先頭に毎秒変わる時刻を入れたり、途中でツール定義を並べ替えると鎖が切れ、毎回全文Prefill再計算（コスト10倍・TTFT悪化）。
・OK：固定の指示とツール定義を最上部に置き、会話と観察結果は末尾にだけ足す。
疑問②：なぜプロンプトで「JSONで出して」と書くだけではダメなのか？ プロンプトは「JSONっぽい単語のLogits（点数）を高める」だけであり、余計な挨拶（"Here is the JSON:"）や閉じカッコ忘れの確率を厳密に 0% にはできないため［Qiita harusato2806］。 ・NG：プロンプトだけで祈り、正規表現パースとリトライループで凌ぐ。
・OK：Structured Outputs（Outlines / XGrammar）を有効にし、文法違反トークンのLogitを -∞ にマスクして構文を100%強制する。
疑問③：なぜツール実行結果を返すとき、前回の thinking ブロックを消してはいけないのか？ ツール呼び出しの合間に考えた Interleaved Thinking のブロックは、モデルにとって「なぜそのツールを呼んだか」の作業記憶（KVキャッシュ）そのものであり、改ざん防止の暗号署名（signature）が付いているため［Anthropic Docs］。 ・NG：トークン節約のために前回の thinking を削ってツール結果だけ返すと、APIが400エラーで拒否するか思考の一貫性とKVキャッシュが崩壊する。
・OK：受け取った thinking ブロックは1文字も変えずそのまま返送する。

専門用語 一言での身近な例え 正確な意味と、次のステップ（中級〜特級）での見どころ
① Prefill / TTFT 質問文の「一気読み」と
最初の1文字目が出る時間		 プロンプト全トークンを並列で一括計算し初期KVキャッシュを作る工程。GPUの計算力（FLOPs）が勝負になる（→ 中級 Rank I：FlashAttention）。
② Decode / TPOT 返事の「1語ずつ書き出し」と
1語あたりの間隔時間		 自己回帰で1トークンずつ順番に生成する工程。毎回モデル重みとKVキャッシュをメモリから読み出す「メモリ帯域（Memory Wall）」が勝負になる（→ 中級 Rank I：RooflineとMBU）。
③ KV Cache & PagedAttention 読んだ文の「計算メモ帳」と
「ルーズリーフ式整理術」		 過去トークンのKey/Valueを保存するメモリ。最初から大きな連続ノートを用意すると6〜8割が白紙で無駄になるため、16語ずつの小ページに分けて管理する（→ 中級 Rank I：PagedAttention）。
④ Prefix Caching / Radix木 複数の質問での
「共通メモの使い回し」		 システム指示や過去ターンのKVブロックをハッシュ辞書（vLLM）や木構造（SGLang RadixAttention）で保持し、次回のPrefill計算を丸ごとスキップする（→ 上級 Rank II）。
⑤ Logits & Sampling 全単語の「生の得点表」と
「ハズレを抜いたくじ引き」		 全語彙の得点（Logits）を確率（Softmax）に変え、Top-pやMin-pで低確率のゴミ候補を切り捨ててから次の1語をランダム選択する（→ 上級 Rank II）。
⑥ FSM / PDA Logit Mask 文法ルールによる
「違反くじの黒塗り除外」		 正規表現（FSM: Outlines）や文脈自由文法（PDA: XGrammar）で、次に許されない全トークンのLogitを -∞ にマスクして100%構文を守る（→ 上級 Rank II）。
⑦ Test-Time Compute テスト本番中に使う
「下書きと検算の時間」		 事前学習でモデルを巨大化する代わりに、推論時に <think> トークンを長く生成させたり複数案をPRMで比較して難問を解くパラダイム（→ 特級 Rank III：Snell+ / s1）。
⑧ GRPO 強化学習 先生なしで複数答案を比べる
「グループ内切磋琢磨」		 1問に複数の回答を出させ、グループ平均より正解に近いものを伸ばす強化学習。価値予測モデル（Critic）を省き長い自己検証を創発させた（→ 特級 Rank III：DeepSeek-R1）。

⑥ 整形（Format）≠ 正しさ（Truth） 設計の境界線
Constrained DecodingでJSONスキーマを100%守らせても、中身に「もっともらしい嘘の数値」が入ることは防げない。「形の保証はデコーダ（Logitマスク）」「意味の保証は外側の検証コード」と役割を分ける。

基本の対比①：プロンプトによる指示（ソフトな誘導）vs Constrained Decoding（ハードな物理制約） XGrammar Docs / Qiita
プロンプト指示：文脈を通じて「望ましいトークンの点数（Logits）を高く寄せる」だけなので、低確率でルール違反が漏れる。
Constrained Decoding（Logitマスク）：サンプリング直前に文法違反トークンの点数を -∞（確率 0%）へ書き換えるため、モデルがどれほど混乱していても構文違反は物理的に出力できない（ただしプロンプトにも形式を書いて分布を揃えるのがベスト［XGrammar Docs L21］）。
基本の対比②：事前学習スケーリング（Training-Time）vs 推論時スケーリング（Test-Time Compute） Snell+ (2025) / mkj (Zenn)
Training-Time Scaling：モデルのパラメータ数（7B→70B→671B）と学習データ量を増やして「地頭（重み）」を大きくする従来の方法。
Test-Time Scaling：モデルサイズはそのままに、推論時に「長く考えさせる（Sequential: <think>）」または「複数案を出して選ぶ（Parallel: Best-of-N / PRM）」ことで、必要な難問にだけ計算リソースを集中投下する新しい方法。
基本の対比③：System 1（即答モード）vs System 2（Extended / Interleaved Thinking モード） Kahneman / Lilian Weng (2025)
System 1（通常生成）：質問の直後にいきなり最終回答トークンを1語ずつ出し始める（速くて安いが、複雑な推論や多段ツール計画で浅いミスをする）。
System 2（Thinkingモード）：回答や各ツール呼び出しの前に [thinking] ブロックを生成して仮説検証・計画修正（KVキャッシュへの下書き蓄積）を行ってから行動する。
